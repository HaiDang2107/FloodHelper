\section{Architecture design}
\subsection{Software architecture selection}

To meet the complex requirements and urgency of the FloodHelper system, the project adopts a combination of the Client-Server model and the Publisher-Subscriber architecture as the overall foundation. Theoretically, the Client-Server model strictly separates the roles of the client (interaction) and the server (centralized processing). Meanwhile, the Publisher-Subscriber pattern decouples message senders (Publishers) from receivers (Subscribers) via an intermediary (Broker), making it highly optimal for real-time data flows. Applied practically to FloodHelper, alongside standard HTTP communication, this architecture is actualized through the MQTT protocol. The mobile application acts as a Publisher, continuously broadcasting urgent data packets (such as location coordinate updates), while the Server and web management system act as Subscribers listening to specific topics. This ensures immediate processing and rescue map updates, maintaining continuity even in unstable network conditions.

    \centering
    \includegraphics[width=0.6\textwidth]{Figure/ArchitectureDesign/SoftwareArchitecture.png}
    \caption{Software Architecture}
    \label{fig:Fig411a}
\end{figure}

Diving into the internal structure, the Client application moves beyond traditional MVVM by dividing the system into two distinct main layers: the ui layer and the data layer. The ui layer comprises Views and ViewModels (state management), while the data layer handles API interactions via Repositories, Services, DTOs, and Mappers. A significant architectural enhancement is the introduction of a domain buffer layer in between, acting as a framework-independent zone for data conversion. This architecture strictly adheres to a unidirectional dependency rule: upper layers can only call lower layers, and upper layers react to lower-layer changes via an observation mechanism (watch). The entire initialization and Dependency Injection (DI) process on the Client is automated using the Riverpod package.

On the server side, a Layered Architecture is utilized to organize the source code into horizontal layers with distinct responsibilities, where the data flow moves unidirectionally downwards. This is realized through three components: Controller (receiving HTTP requests and routing), Service (handling core business logic), and Repository (executing database queries). To couple these layers loosely and adhere to the Inversion of Control (IoC) principle, the backend thoroughly leverages the built-in Dependency Injection mechanism of the NestJS framework. The consistent application of DI across both client and server ensures that components operate independently, enhancing maintainability and facilitating the automated testing process.

\subsection{Overall design}

The overall architecture of the FloodHelper system is modeled through UML Package Diagrams, clearly demonstrating the separation of layers and strict dependency management principles. The packages are organized following a unidirectional dependency rule: the design ensures no circular dependencies, upper-layer packages depend on lower-layer packages, lower-layer packages strictly do not depend on upper ones, and the call flow does not skip layers. To provide a comprehensive view, the system design is divided into three diagrams: General Package Diagram, Package Diagram for Frontend, and Package Diagram for Backend.

\subsubsection{General package diagram}

The general diagram outlines the highest-level structure of the entire system. This structure comprises three main blocks: \textit{frontend}, \textit{backend}, and \textit{client\_server}. Here, \textit{frontend} and \textit{client\_server} act as clients, maintaining a one-way dependency on the \textit{backend} for data exchange and retrieval. Internally, both the \textit{frontend} and \textit{backend} blocks are subdivided into smaller packages that adhere strictly to layered design principles.

\subsubsection{Package diagram for backend}

The backend architecture is designed with two distinct layers: the \textit{feature} layer (business logic) positioned at the top and the \textit{common} layer (shared infrastructure) at the bottom. The \textit{feature} layer depends on \textit{common} for resources, while \textit{common} operates entirely independently.

Package \textit{feature}: Contains packages handling the core business logic of the application, including \textit{charity} (charity campaign management categorized by \textit{authority} and \textit{user}), \textit{admin} (system administration), \textit{authentication} (user authentication), \textit{profile} (profile management), \textit{role\_request} (handling permission requests), \textit{signal} (transmitting and receiving distress signals), \textit{announcement}, \textit{address}, and \textit{friend} (rescue contact management).

Package \textit{common}: Provides shared tools and infrastructure connections utilized across the entire backend. This layer encompasses \textit{prisma} (the ORM for database interactions), \textit{vietqr} (payment/donation gateway integration), \textit{firebase} (push notification services), and \textit{cloud} (file storage services).

\subsubsection{Frontend subsystem}

The design strictly adheres to the MVVM pattern and Clean Architecture, ensuring a unidirectional data flow.

Package \textit{ui.user.home}: The core of the interface is the \textit{HomeScreen} class. This class uses aggregation to integrate smaller UI components like \textit{HomeMapPin}, \textit{UserLocationPin}, \textit{PinActionBubble}, and \textit{HomeTopActions} to render the overview map. For user interactions, \textit{HomeScreen} has a dependency on \textit{DistressSignalSheet} (for signal creation) and \textit{BroadcastingSignalsSheet} (for viewing broadcasting signal lists). Logically, \textit{HomeScreen} depends on \textit{HomeViewModel}. Following the design pattern, the ViewModels (\textit{HomeViewModel} and \textit{BroadcastingSignalsViewModel}) have a strict composition relationship with their respective state classes (\textit{HomeState} and \textit{BroadcastingSignalsState}).

Package \textit{data}: To decouple the UI logic from data retrieval, the ViewModel only depends on the \textit{SignalRepository} interface. The \textit{RealSignalRepository} class provides the implementation of this interface. The \textit{RealSignalRepository} maintains an aggregation relationship with underlying services such as \textit{SignalService} (which calls APIs via \textit{ApiClient}), \textit{SosLocalStorage}, and \textit{BroadcastingSignalsLocalStorage}.

To support real-time processing, the \textit{HomeViewModel} depends directly on the \textit{LocationTrackingService}. This service manages the background isolate/process (\textit{LocationTrackingBackground}), which in turn depends on the \textit{MqttService} to stream coordinates continuously via the MQTT protocol. Additionally, the \textit{GlobalNotificationController} in the \textit{common} package aggregates the \textit{FirebaseMessagingService} to handle global push notifications.

\subsubsection{Backend subsystem}

On the backend, the Layered Architecture is clearly demonstrated through the separation of responsibilities.

The \textit{SignalController} class is responsible for receiving requests and maintains a dependency on the \textit{SignalService}.

The \textit{SignalController} also depends on a set of Data Transfer Objects (\textit{dto} package) such as \textit{ChangeSignalState}, \textit{CreateSignal}, etc., to validate and standardize inputs and outputs.

The \textit{SignalService} encapsulates the business logic and depends on the \textit{SignalRepository}. Finally, the \textit{SignalRepository} depends on the \textit{PrismaService} (located in the \textit{common.prisma} package) to execute direct queries against the PostgreSQL database.

\subsubsection{Client server subsystem}

To offload processing from the main backend API, the system employs an independent Worker.

The \textit{MqttWorker} class has an aggregation relationship with \textit{BackendApiClient} and \textit{Settings}. This class acts as a subscriber, listening to coordinate data streams over MQTT, and depends on the backend infrastructure to update rescue data in real-time without disrupting the primary HTTP traffic flow.

\subsubsection{UI conventions}

The user interface design system of FloodHelper is built upon three core criteria: clarity, speed, and safety. Regarding the color palette, the project utilizes dark blue as the primary color to convey reliability, combined with a light background for the web platform and dark mode for mobile to optimize battery life during power outages. A crucial emphasis is placed on the strictly regulated semantic color system: red is exclusively used for emergencies (SOS), orange for risk warnings, and green indicates safety or a successful status. To ensure optimal legibility across all devices, the system employs modern sans-serif fonts such as Inter or Roboto, featuring a clear size hierarchy ranging from large headings (24-32px) to caption text (12px).

Interactive components, such as buttons and input fields, are designed with a transparent visual hierarchy to guide the user. Primary action buttons consistently stand out with a solid background color and rounded corners (8px on Web and 12-16px on Mobile for easy tapping), whereas secondary or text buttons feature a more minimalist design with outlines or no borders. Input fields and controls (checkboxes, radio buttons, toggles) are all mandated to have a minimum touch target size (e.g., 44px on Mobile) and display a blue border effect when focused. All user interactions, including pressing, hovering, or disabled states, provide synchronized visual feedback to simulate a realistic tactile feel.

In terms of spatial organization and navigation, the web interface utilizes a 12-column grid system with a left sidebar to accommodate a spacious administrative workspace, while the mobile platform optimizes a 4-column grid combined with bottom and right navigation bar for thumb-friendly reachability. The feedback messaging system is layered by priority: quick notifications (Toasts) appear at the bottom edge on mobile or the top corner on web, input errors are highlighted in red in real-time (Inline Validation), and critical decisions require a centralized modal dialog with a dimmed background overlay. Finally, all icons within the system adhere to a unified stroke style, with a strict mandatory rule: life-or-death functions like SOS or location sharing must always be accompanied by text labels and absolutely never stand alone to prevent any misinterpretation during moments of user panic.

\subsubsection{Sequence Diagram}

To further illustrate the dynamic interactions between the designed classes, the following sequence diagrams detail the execution flow of two core use cases in server side: Broadcast Signal and Handle Signal. These diagrams map out the exact sequence of method calls across the Controller, Service, and Repository layers.

The sequence diagram in figure \ref{fig:Fig422a} demonstrates the execution flow when a user initiates a new distress signal. The process begins with the \texttt{SignalController} receiving the creation request and delegating it to the \texttt{SignalService}. First, the service queries the \texttt{SignalRepository} to ensure the user does not already have an actively broadcasting signal. Once validated, the system persists the new signal entity in the database. To alert the appropriate personnel, the service retrieves the creator's profile via the \texttt{UserRepository} to identify their specific ward and subsequently fetches a list of available rescuers within that area. Finally, the \texttt{FirebaseService} dispatches a multicast push notification to these designated rescuers, while the system iteratively logs a formal system announcement for each rescuer through the \texttt{AnnouncementRepository}.

\subsection{Database design}

The FloodHelper database is designed to support the system's core functionalities, including user management, social networking, emergency rescue coordination, charity campaign management, and real-time communication. The database follows a relational model implemented using PostgreSQL, providing a structured and consistent mechanism for storing application data.

As illustrated in Figure \ref{fig:Fig423a}, the database schema is organized into several functional modules. The user management module is centered around the User entity, which stores user information and is associated with entities such as Account, Profile, Session, and Provider to support authentication, profile management, and session tracking. Social networking functionalities are implemented through entities including Friendship, FriendMakingRequest, Post, Comment, and Like, enabling users to establish relationships and interact with shared content.

\begin{figure}[H]
    \centering
    \includegraphics[width=\textwidth]{Figure/DatabaseDesign/ERD.png}
    \caption{Entity-relationship diagram}
    \label{fig:Fig423a}
\end{figure}

The charity campaign module manages fundraising activities through entities such as CharityCampaign, Transaction, Supply, FinancialSupport, and AnnouncementFromBenefactor. These entities record campaign information, donation transactions, relief item distribution, and campaign announcements, while Bank and BankAccount provide the information required for donation processing and financial transparency.

Emergency rescue operations are supported by the Signal entity, which stores distress requests submitted by victims and the associated rescue information. In addition, communication between users is facilitated through ChatRoom, RoomMember, and Message, while geographical reference data are maintained using the Province and Ward entities. The WeatherMap entity stores weather information that supports rescue-related functionalities.

The relational database schema is derived from the conceptual design by defining primary keys, foreign keys, and integrity constraints to preserve data consistency and relationships among entities. UUID is adopted as the primary key type for most entities to provide globally unique identifiers suitable for distributed applications. \section{Testing}

To verify that the FloodHelper ecosystem operates reliably under field conditions, a multi-layered testing strategy was implemented. The testing workflow covers individual components, data pipelines, real-time protocols, and interactive user journeys.

\subsection{Testing methodology and techniques}

The system quality assurance process was conducted across three distinct testing levels:
\begin{itemize}
    \item Unit testing: Implemented on the NestJS backend (using Jest) to test services, and on the Flutter frontend (using Flutter Test) to verify Riverpod view models and business validation logic.
    \item Integration and E2E testing: Focused on data transfers between the mobile client, the Python MQTT Worker, the NestJS server, and the database. Payment callbacks (VietQR hook) were also validated.
    \item UI and widget testing: Performed UI verification using Flutter's widget testing framework. This includes golden image rendering tests to ensure map pins and role badges render consistently across varied resolutions.
\end{itemize}

The test cases were designed using the following techniques:
\begin{itemize}
    \item State transition testing: Used to verify status transitions for SOS signals (\texttt{BROADCASTING} $\rightarrow$ \texttt{HANDLED} $\rightarrow$ \texttt{STOPPED}) and charity campaigns (\texttt{Pending} $\rightarrow$ \texttt{Approved}/\texttt{Rejected} $\rightarrow$ \texttt{Finished}) without deadlock.
    \item Equivalence partitioning (EP) and boundary value analysis (BVA): Utilized to define validation boundaries for geographic coordinates, integer limits (such as trapped victims count), and payment limits.
    \item Use case testing: Developed based on user stories representing critical field actions to verify collaboration across multiple systems.
\end{itemize}

\subsection{Retrospective: failure analysis and resolutions}

During development testing cycles, several test runs initially failed. A retrospective analysis details the root causes and the engineering solutions implemented:

\begin{itemize}
    \item Background location tracking failures: Android OS power-saving routines put the background location collection to sleep after 10 minutes. This was resolved by wrapping the background isolate inside a native foreground service using the \texttt{flutter\_background\_service} plugin and showing a persistent notification.
    \item State synchronization delay in SOS handling: When a rescuer accepts a victim's request, a handling confirmation message is sent to the MQTT worker. However, due to network transit time, the victim's device may not receive this confirmation immediately and continues to broadcast active SOS signals. As a result, the victim's distress pin fails to disappear from the rescuers' map interfaces. This was resolved by implementing a short-term caching mechanism on the MQTT worker: when a "handled" event for Victim X is processed, their ID is temporarily cached for 10 seconds. If any further SOS packets are received from Victim X during this time window, the worker intercepts the packet and mutates the \texttt{sos} status flag to \texttt{false} before forwarding it, ensuring consistent map UI updates across all clients.
\end{itemize}
