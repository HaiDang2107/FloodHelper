\label{sec:methodology}

This section describes the technology stack, services, and development tools selected for the FloodHelper system. The selection is based on their suitability to meet specific system demands: real-time location sharing under unstable network conditions, transactional integrity for donation management, and cross-platform accessibility.

\section{Frontend framework: Flutter}
Flutter \cite{flutterwebsite} is selected to develop the mobile application for both normal users (victims) and rescuers. In the FloodHelper system, the mobile app must handle real-time location updates, render interactive maps (utilizing OpenStreetMap \cite{osmwebsite}), and update UI states dynamically. Flutter is chosen because it renders UI components directly using its own graphic engine (Skia/Impeller). This direct rendering ensures smooth map interactions and continuous background rendering, which are critical when victims and rescuers need to track coordinates in emergency situations. Furthermore, Flutter enables development for both Android and iOS from a single Dart codebase, significantly reducing development and maintenance overhead.

\section{Backend framework: NestJS}
The backend server of the system is built using NestJS \cite{nestjswebsite}, a progressive Node.js \cite{nodejswebsite} framework. The backend is responsible for processing REST API requests, coordinating real-time message routing, and managing transactional workflows such as role applications and charity campaigns. NestJS is selected over Express.js \cite{expressjswebsite} because of its opinionated, modular architecture (modules, controllers, and services). This structure prevents code degradation as the system grows and ensures that critical donation logic is separated from authentication and notification systems. Additionally, NestJS's native support for TypeScript provides compile-time type safety, minimizing runtime exceptions in processing financial records and emergency states.

\section{Database management: PostgreSQL}
PostgreSQL \cite{postgresqlwebsite} is chosen as the primary relational database to store persistent records, including user profiles, emergency signal histories, and campaign transaction logs. In a system managing charitable donations, transactional reliability is paramount. PostgreSQL's strict ACID (Atomicity, Consistency, Isolation, Durability) compliance guarantees that donation operations are recorded accurately without data corruption during concurrent write-heavy events. Compared to MySQL \cite{mysqlwebsite}, PostgreSQL offers superior support for complex queries and extensibility for potential geospatial indexing, which is necessary for geographic search operations in flood areas.

\section{Object-relational mapping: Prisma ORM}
To interact with the database, the backend utilizes the Prisma \cite{prismawebsite} Object-Relational Mapper (ORM) instead of TypeORM \cite{typeormwebsite}. Prisma is selected because it uses a centralized, human-readable schema file (`schema.prisma`) as the single source of truth, automating database migrations. Prisma auto-generates a strongly-typed database client, ensuring that database queries in NestJS are validated at compile-time, which eliminates common database query errors during execution.

\section{Real-time communication: MQTT and EMQX cloud}
Real-time communication is crucial for distress broadcasting and rescuer coordination. The system utilizes MQTT \cite{mqttwebsite} (Message Queuing Telemetry Transport) as the primary protocol for real-time location tracking and signal sharing. Unlike HTTP or standard WebSockets, MQTT has an extremely lightweight header size (minimizing bandwidth consumption) and operates on a Publish/Subscribe model. This is essential for FloodHelper, as victims often broadcast signals in areas with degraded mobile networks. MQTT's built-in Quality of Service (QoS) levels guarantee that critical SOS signals and location updates are retried and delivered once a connection is re-established.

The system uses EMQX cloud \cite{emqxwebsite} as the managed MQTT broker to route messages between the mobile clients and the backend. EMQX cloud is selected over a self-hosted broker because it is built for distributed clustering, allowing the system to scale automatically and handle spikes in concurrent connections during active flood disasters without manual infrastructure administration.

On the server side, Python with the `paho-mqtt` \cite{pahomqttwebsite} library is used to run background processes that listen to incoming location streams. Python's event-driven, asynchronous client handles high-frequency location data from EMQX cloud without blocking the main NestJS API server, maintaining optimal server responsiveness.

\section{Support services and infrastructure}

\subsection{Cloud storage: Cloudinary}
Cloudinary \cite{cloudinarywebsite} is integrated to manage dynamic media assets, such as images uploaded for charity verification campaigns or user profiles. In disaster zones, network speed is highly limited. Cloudinary is chosen because it allows on-the-fly image optimization and resizing via URL parameters, reducing the file size delivered to mobile devices. Images are served through a global Content Delivery Network (CDN), offloading bandwidth from the primary backend server and ensuring fast image loading on the mobile client.

\subsection{Push notifications: Firebase Cloud Messaging}
Firebase Cloud Messaging (FCM) \cite{firebasefcmwebsite} is employed to deliver push notifications, such as emergency alerts, rescue status updates, and announcement broadcasts. Since the mobile app must alert users even when it is running in the background or closed, FCM is selected as it is natively supported by both Android and iOS notification systems. It supports topic-based subscription, allowing the backend to broadcast notifications to all users in a specific ward simultaneously.

\subsection{In-memory caching: Redis}
Redis \cite{rediswebsite} is utilized as an in-memory database to store temporary, high-frequency data such as One-Time Passwords (OTPs) for phone authentication and user session states. Storing these short-lived tokens in Redis prevents unnecessary write operations to the primary PostgreSQL database. Redis's sub-millisecond read/write latency and automatic Time-To-Live (TTL) expiration ensure rapid, secure authentication workflows.

\subsection{Containerization and hosting: Docker and Render}
Docker \cite{dockerwebsite} is used to containerize the NestJS backend and PostgreSQL database, packaging the applications with their exact environment configurations. This guarantees consistency between the developers' local environments and the production servers, eliminating deployment discrepancies.

Render \cite{renderwebsite} is selected as the cloud hosting provider for the backend services. Render is chosen over complex cloud providers (such as AWS or Google Cloud) because it provides a fully managed Platform-as-a-Service (PaaS) with integrated Git-based CI/CD. This automates the build and deployment process of the Docker containers whenever code is merged, reducing operational overhead and allowing the project to focus on feature implementation.

\section{Development tools}

Visual Studio Code \cite{vscodewebsite} serves as the primary Integrated Development Environment (IDE) for writing, formatting, and debugging the codebase across both the frontend and backend services. It is chosen for its extensive extension ecosystem, which supports development in both Dart and TypeScript.

For version control and collaborative development, Git \cite{gitwebsite} and GitHub \cite{githubwebsite} are employed to manage repository history, track feature updates, and maintain code quality through pull request workflows. This setup ensures codebase consistency and enables seamless team collaboration.

Finally, Postman \cite{postmanwebsite} is used to perform API testing, allowing developers to execute, validate, and document REST API requests and responses during development. It helps verify backend route correctness before integrating them into the frontend.
